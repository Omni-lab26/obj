# バグ探しのプロンプト

Lento（このリポジトリの `ambient/`）のバグを、抜けなく探して報告させるためのプロンプトです。

**使い方**
1. 下の「2. ユーザーが見つけた症状」に、気づいたバグを書き足します（何をしたら、何が起きたか、どの端末か）。
2. Claude Code のセッションで「`ambient/docs/bug-hunt.md` のプロンプトを実行して」と頼みます。新しいセッションでも、このファイルだけで分かるように書いてあります。
3. 報告は `ambient/docs/bug-report-<日付>.md` にまとまります。直すのは、報告を読んでから別に頼みます。

---

## 0. やること

あなたはこのアプリのバグを探す担当です。目的は**実際に起きるバグを、証拠つきで、漏れなく見つけて報告すること**です。

- 直さないでください。アプリのコード、`scenes/`、設定ファイル（`app.json`、`eas.json`、`store.config.json` など）には手を触れません。
- 書いてよいもの：
  - 報告ファイル `ambient/docs/bug-report-<YYYY-MM-DD>.md`
  - スクラッチパッドに置く検証用のスクリプトとスクリーンショット
- コミットするのは報告ファイルだけです。作業ブランチにコミットしてプッシュします。

## 1. 守ること

**すべての指摘に証拠をつけます。**
1件ごとに「再現手順」「期待した動き」「実際の動き」「原因の場所（`file:line`）」をそろえます。

**実機でしか確かめられないものは、確からしさを分けて書きます。**
ウェブ版では再現できず実機でしか確かめられないものは、その旨を書いたうえで、次のどれかに分けます。
- **要実機**：コードを読んで、具体的な入力からその失敗まで筋道をたどれたもの
- **疑い**：筋道はたどれないが、怪しいもの

**誤報は見逃しと同じくらい高くつきます。**
報告の前に、各指摘を自分で崩しにいってください。
- 本当にその経路を通るか
- 別の場所で防がれていないか
- 意図した仕様ではないか

崩せなかったものだけを報告します。

**次のものはバグとして報告しません。**
- 書き方の好み、リファクタリングの希望
- 測っていない「重そう」
- 意図した仕様（下に書いたもの）

**意図した仕様（バグではない）**
- 画面はスリープしない（置き時計なので、わざと）。
- 画面のどこかを長押しすると、時計の表示と非表示が切り替わる。
- タップすると、下の背景切り替え、左上のペン、右上の設定のボタンが出て、約3.5秒で消える。
- アプリを閉じている間に終わったタイマーは、次に開いたとき音も振動もなく「終了」になる（`src/timers.ts` の `useTimerAlarm`）。
- 写真の背景は今は0枚なので、設定の「デジタル」の項目は出ない。
- 数字の位置と大きさは、縦向きと横向きで別々に覚える（`face` と `faceWide`）。

**仕様の穴は、バグと分けて短く書きます。**
「仕様どおりだが、使う人は困りそう」というものです。たとえば、アプリが裏にあるときにタイマーが終わっても知らせる手段がない、など。

**ウェブ版だけの問題は優先度を下げます。**
ウェブ版（react-native-web）でだけ起きて、iOS では通らないコードの問題は、優先度を下げて別に書きます。どちらでも同じコードを通るなら、ふつうに報告します。

## 3. アプリについて知っておくこと

**何のアプリか**
- 動く背景の上に、大きな時計・タイマー・ストップウォッチを置いておく置き時計アプリ。
- iPhone と iPad、縦横どちらにも対応。日本語と英語。
- 何時間も、何日もつけっぱなしで使われる前提。

**技術**
- Expo SDK 58、React Native 0.88。
- Reanimated 4、Gesture Handler 3。
- 背景は HTML のシーンで、iOS では WebView、ウェブ版では iframe で動く。

**バージョン**
- App Store に出ている **1.0 はビルド 4** で、コミット `1ef90fa`（タイマーの目盛りの作り直し）より前のもの。正確なコミットは EAS のビルド一覧（`gitCommitHash`）で確かめられる。
- ブランチの先頭は、これから出す **1.0.1** の候補。
- 調べるのはブランチの先頭。見つけたバグごとに、`git log` や `git blame` で **1.0 にもあるか** を書く。

**ファイルの地図**

| ファイル | 中身 |
| --- | --- |
| `App.tsx` | 全体：背景の切り替え、ボタンの表示と非表示、長押し、アプリが裏に回ったときの一時停止（`AppState`）、スリープ防止 |
| `src/Clock.tsx` | 時計・タイマー・ストップウォッチの数字、左右スワイプでのモード切り替え、編集（移動・拡大縮小）、拡大中と止まったあとの数字の重ね方 |
| `src/TimeScrubber.tsx` | タイマーの目盛り（ドラッグ、慣性、端のたわみ、振動） |
| `src/TimerSaves.tsx` | よく使うタイマーの保存枠（5つ、タップで保存・呼び出し、長押しで削除） |
| `src/timers.ts` | タイマーとストップウォッチの計算（壁時計の時刻で持つ）、終了の知らせ |
| `src/settings.tsx` | 設定の型、初期値、保存（AsyncStorage、キー `ambient.settings.v1`、250ms 遅れて保存）、古い保存データの補い（`withDefaults`） |
| `src/SettingsSheet.tsx`、`src/ColorField.tsx` | 設定画面（フォント8種、色、日付・秒・24時間、言語、使い方をもう一度） |
| `src/Tips.tsx` | 初回の吹き出しでの案内 |
| `src/SceneView.tsx`、`src/SceneView.web.tsx` | 背景を WebView や iframe で動かす。tap、longpress、ready のメッセージをやりとりする |
| `src/scenes.ts`、`src/scenes.generated.ts` | 背景の一覧（koi、sharks、manta、nightsharks、shrine、blank、walkers）。generated は `scenes/` から作られる |
| `src/i18n.ts`、`src/fonts.ts`、`src/colors.ts` | 文言、フォント、色 |
| `scenes/shared/host.js` | 全シーン共通：キャンバスの大きさ、フレームの繰り返し、一時停止、タップと長押しの判定 |
| `scenes/shared/ascii-sea.js` | 鯉、サメ、マンタ、夜のサメの共通エンジン（魚の泳ぎ、エサ、驚いて逃げる、時計の周りを避ける） |
| `scenes/shrine.html` | 神社（WebGL。WebGL が使えないときは 2D で描く） |
| `scenes/walkers.html` | 通りすがり |

**テスト用の仕掛け（シーンの URL の `#` の後ろに付ける）**
- `#seed=N`：乱数を固定する。
- `#hold`：自動では進めない。
- `#probe`：中の状態を外から見られるようにする（`window.__seaFish`、`window.__seaPads`、`window.__shrine`）。
- `window.__ambient.step(dt)`：1フレームずつ手で進める。
- `window.__ambient.pause()`、`window.__ambient.resume()`：止める、動かす。

## 4. 準備

`ambient/` で次を実行します。

```sh
npm ci                                   # node_modules が無いときだけ
node scripts/build-scenes.mjs
npx tsc --noEmit
CI=1 npx expo lint
rm -rf dist && npx expo export --platform web --output-dir dist
python3 -m http.server 8765 -d dist      # バックグラウンドで動かす
```

ブラウザは Playwright を使います。
- Chromium は入っているので、`require('playwright')` してそのまま `chromium.launch()` するだけです。`playwright install` はしないでください。
- 起動前に `localStorage` の `ambient.settings.v1` に設定を入れておくと、狙った状態から始められます。例：`{"mode":"timer","scene":"shrine","tipsSeen":true,"langChosen":true,"lang":"en"}`
- 読み込んだあと約4秒は起動の演出があります。待ってから操作してください。
- 試す画面サイズ：
  - iPhone：390×844、844×390、375×667（SE）、440×956（Pro Max）
  - iPad：1032×1376、1376×1032
  - iPad の Split View と Slide Over を想定した細長い画面：320×1024、507×1024、694×1024
- 言語：ja と en の両方。

## 5. 調べる範囲

全部を見て、各項目に「問題あり」「問題なし（どう確かめたか）」「調べられなかった（理由）」のどれかを残してください。

### A. 時計
- 分と時の繰り上がり、日付の変わり目（23:59→0:00）。時刻は Playwright の `page.clock` などで進められます。
- 12時間と24時間、秒あり・なし、日付あり・なしの組み合わせ。
- フォント8種それぞれで、数字が変わるときに幅が揺れたり、位置が飛んだりしないか。
- 日本語と英語の日付の書き方。長い曜日や月の名前がはみ出さないか。
- 時間帯や夏時間が切り替わったとき、端末の時刻を手で変えたとき（実機の項目）。
- 色を「シーンに合わせる」にしたとき、明るい背景と暗い背景で数字が読めるか。

### B. モードの切り替え（左右スワイプ）
- 時計・タイマー・ストップウォッチがぐるぐる回るか。
- 速く続けてはじいたとき、1回に1ページだけ進むか。
- モード名の出方と消え方。
- 途中で指を戻したり、縦に動かしたり、2本指になったりしたとき。
- 編集中や設定画面を開いている間にスワイプしたとき。
- 回転したとき、ページがずれて止まらないか。

### C. タイマー
**目盛り**
- 上限と下限：時間は 0〜23、分秒は 0:00〜59:45 で、15秒刻み。
- 端を越えたときのたわみ。
- 慣性で滑ってからぴたりと止まるか。
- 2本の目盛りを同時に触ったとき。
- 目盛りの値と数字の表示がずれないか（`dial` と `duration`）。

**動かし方**
- 開始・一時停止・再開・終了後のタップ・長押しでのリセットが、それぞれ正しく動くか。
- 0秒のままでタップしたとき。
- 動いている最中に目盛りを触ったとき。

**終わるとき**
- アプリが前にあるときに、振動と表示が正しいか。
- アプリが裏にあるとき、画面がロックされているとき、アプリが終了されているとき。
- 戻ってきたとき、表示と状態が正しいか。
- `endAt` が保存されて、再起動しても正しく続くか。

**保存枠**
- 5つ埋まったとき、同じ長さを2回保存したとき。
- 削除したあとの並び。
- 保存枠を呼び出したあとの目盛りの位置。

**表示**
- 数字がスロットのように回る演出が、止まったときにぴたりとそろうか。
- 23:59:45 のときの表示。

### D. ストップウォッチ
- タップで開始・停止、長押しでリセット。
- 長く動かしたとき：24時間、100時間（`formatFixed` は時の桁が3桁になる）。桁が増えたときに、はみ出したり大きさが変わったりしないか。
- 再起動しても続くか。
- 時計を戻したとき（端末の時刻が過去になる）、時間がマイナスにならないか。

### E. 数字の編集（ペン）
- 1本指で動かす、2本指で拡大縮小する。
  - 最小は 0.35 倍、最大は画面に入る大きさまで。
  - 限界まで行ったとき、枠が赤くなるか。
- 拡大縮小の最中と離したあと：
  - 数字のちらつき。
  - 枠の外に数字が出る「ゴースト」。
  - 動いている間の数字と、止まったあとのくっきりした数字の位置が1ピクセルでもずれないか。
  - 離したあとの数字が粗くないか。
- 縦向きと横向きで、別々に覚えているか。
- 編集中に回転したとき、編集中にモードを変えたとき。
- 画面の外に数字を追い出せてしまわないか。
- 画面サイズが変わったとき（iPad の Split View）、前に覚えた位置が画面からはみ出さないか。
- 「完了」で確定するか。完了しないまま裏に回したときにどうなるか。

### F. ボタン、案内、設定
- タップでボタンが出る、約3.5秒で消える、長押しで時計の表示と非表示。
- ボタンを押した直後に消えて押し損ねないか。
- 初回の案内：順番、スキップ、設定の「使い方を見る」でもう一度見られるか。案内の途中で回転したとき。
- 設定の各項目がすぐに反映され、再起動しても残っているか。
- 言語を切り替えたとき、全部の文言が変わり、はみ出さないか。
- 色の選択（`ColorField`）：端、つまみの動き、選んだ色の保存。
- 背景の切り替え：左右の矢印、ドットの数（7つ）、最後に見た背景で起動するか。

### G. 保存と移行
- 保存データが壊れているとき（JSON でない、型が違う、項目が足りない）に、落ちずに初期値で起動できるか。
- 保存された背景 ID がもう無いとき（例：`"scene":"photo-x"`）。保存されたフォント ID がもう無いとき。
- 変更して 250ms 以内に終了したとき、変更が消える範囲。
- 1.0 で保存されたデータを 1.0.1 で読んだとき（`withDefaults` が足りているか）。

### H. 背景（7つすべて）
- それぞれで、次のことを確かめる。
  - 読み込み、タップ、長押し、回転、大きさの変更。
  - 裏に回して戻したときの一時停止と再開。
  - 1フレームにかかる時間。
- **つけっぱなし**：`#hold` と `__ambient.step` で、1時間、24時間、7日分を早送りする。
  - 数値が NaN や Infinity にならないか。
  - 魚や人が画面の外に出たまま戻らない、一か所に固まる、震える、止まる、ということがないか。
  - 配列（落ち葉、エサ、波紋、粒子）が増え続けないか。
  - 時間の折り返しで表示が飛ばないか（例：神社は `t % 1000` で1000秒ごとに折り返す）。
- 魚が時計の周りを避けるか。時計を動かしたり大きくしたりしたあとにも避けるか。
- 神社：
  - WebGL が使えないときの 2D の絵。
  - WebGL の描画環境が失われたあと、復帰するか。
  - 細長い画面で、鳥居が時計に隠れたり、切れたりしないか。
- 通りすがり：タップで驚いて逃げる動き、人どうしがぶつからないか。
- 白紙：数字の色が読めるか。

### I. iOS の実機でしか起きないこと（コードを読んで、筋道をたどる）
- WebView の中身が裏で OS に終了させられたとき（メモリが足りないとき、長く裏にあったとき）。
  - 背景が白や黒のまま戻らないことはないか。
  - `SceneView.tsx` で、中身が終了されたことを受け取っているか。
- 一時停止と再開の指示が、WebView の読み込み前に送られて取りこぼされないか。
- スリープ防止が、裏から戻ったあとも効いているか。
- 低電力モード、視差効果を減らす、文字を太くする、文字の大きさの設定、システムのダークモードとライトモード。
- ノッチやダイナミックアイランドの周り、iPad の Stage Manager。
- 振動（Haptics）が多すぎたり、続けて鳴りすぎたりしないか。

### J. どこにも入らないもの
- コンソールのエラーと警告。React の key の警告、更新が止まらないループ、後片付けされないタイマーやイベントリスナー。
- 同じ処理が2回走る（React の StrictMode や、二重のタップ）。
- 背景のページとアプリの間のメッセージで、想定していない形のものが来たとき。

## 6. 進め方

1. **読む**
   - ファイルの地図の順にコードを読み、5章の項目ごとに怪しい点を挙げる。
   - 挙げたものには、どの入力で、どの行を通って、何が起きるかを書く。
2. **再現する**
   - ウェブ版と Playwright で、実際に起こす。
   - 計算だけで確かめられるもの（`src/timers.ts` など）は、Node で関数を直接呼んで確かめる。
   - スクリーンショットや数値の記録を残す。
3. **崩しにいく**
   - 再現できたものも、本当にバグか疑う。
     - 仕様ではないか。
     - 別の経路で防がれていないか。
     - ウェブ版だけの話ではないか。
   - もう一度、別のやり方で再現する。
4. **書く**
   - 7章の形で報告を書き、コミットしてプッシュする。

**手分けしてもよいです。**
エージェントを分けて並行して調べるなら、次の5つに分けます。
- A＋B
- C＋D
- E＋F
- G＋J
- H＋I

最後に、崩しにいく役を1つ別に置きます。並行して調べるのは、ユーザーが「ワークフローで」「並行して」と頼んだときだけです。

**使うモデル**
- 1人で順に調べるときは、セッションのモデルを **Fable 5.1** にします（`/model claude-fable-5-1`）。指の動きやアニメーションのタイミング、つけっぱなしのときの挙動、実機でしか起きないことなど、コードを読んで筋道をたどる力が要るものが多いからです。アプリは約1万行と小さいので、いちばん賢いモデルで回しても使う量はそれほど増えません。
- 手分けするときは、次のように割り当てます。
  - 範囲ごとに調べる5つの役：**Opus 5.5**
  - 最後に指摘を崩しにいく確認役：**Fable 5.1**（誤報を減らすのにいちばん効くところ）
  - 全体をまとめる役（このプロンプトを受け取ったセッション）：Fable 5.1
- 速さと安さを優先して Sonnet 5.5 にすると、タイミング絡みの細かいバグを取りこぼしやすくなります。Haiku 5.5 は使いません。
- どのモデルでも、考える深さ（effort）は **high 以上**にします。

## 7. 報告の形

`ambient/docs/bug-report-<YYYY-MM-DD>.md` に、日本語で書きます。

**1. まとめ**
- 重さの順に並べた表。列は次のとおり。
  - ID
  - 重さ
  - 一行の説明
  - 場所
  - 確かさ（再現済み／要実機／疑い）
  - 1.0 にもあるか
- 重さの決め方：

  | 重さ | 意味 |
  | --- | --- |
  | S1 | 落ちる、固まる、データが消える、タイマーが鳴らないなど、時計として信用できなくなる |
  | S2 | 主な機能が正しく動かない |
  | S3 | 目に見える表示の乱れ（ちらつき、はみ出し、ずれ） |
  | S4 | 小さなこと |

**2. 1件ずつの詳細**

1件ごとに次をそろえます。
- 再現手順（番号つき）
- 期待した動き
- 実際の動き
- 証拠：スクリーンショットのパス、数値、ログ
- 原因：`file:line` と、なぜそうなるか
- 直し方の見当：1〜2行。直すのは別の作業
- 1.0 にもあるか

**3. 実機で確かめてほしいこと**
- 「要実機」と「疑い」の項目を、ユーザーが iPhone や iPad で試せる手順にする。
- 書くこと：
  - どの端末と向きで
  - 何をして
  - 何が見えたらバグか
- 試す方法は、TestFlight のビルドか、`npm run live` で Expo Go から開くかのどちらか。

**4. 仕様の穴と改善案**
- 短い箇条書き。

**5. 調べて問題なかったこと**
- 5章の項目ごとに、どう確かめたかを1行で書く。どこまで見たかが分かるように。

最後に、ユーザーへの返事として、日本語で次を短く伝えます。
- 見つかった件数を重さごとに
- いちばん重いもの3つ
- 報告ファイルの場所

## 8. 終わりの条件

- 2章の症状は、全部に結論がある（再現して原因まで、または再現できなかった理由まで）。
- 5章の項目は、全部に「問題あり」「問題なし」「調べられなかった」のどれかがついている。
- 報告した指摘は、全部が3の「崩しにいく」を通っている。
- 報告ファイルがコミットされ、プッシュされている。アプリのコードには変更がない（`git status` で確かめる）。
