# アプリ立ち上げテンプレート

Evently・Pawroom・Inchly・Lento の4本の振り返りから作った、新しいアプリの始め方です。
「毎回同じ手順で始める」「同じ手戻りを繰り返さない」ためのもので、ファイル一式と手順書でできています。

---

## 4本に共通していた手戻り

| 手戻り | Evently | Pawroom | Inchly | Lento | 防ぐ場所 |
| --- | :-: | :-: | :-: | :-: | --- |
| MVP と「やらないこと」がなく、作ってから削った | ○ | ○ | ○ | ○ | `docs/brief.md` |
| 見た目を実装しながら試し、何度もひっくり返した | ○ | ○ | ○ | ○ | `docs/design.md` |
| 実機・本番ビルドでの確認が遅かった | ○ | ○ | ○ | ○ | フェーズ3・4 |
| 名前・ID・アイコンを後から決めて作り直した | − | ○ | − | ○ | `docs/brief.md` |
| 画面一覧と遷移がなく、押せない画面が残った | ○ | ○ | − | ○ | `docs/screens.md` |
| 対応範囲（画面幅・OS・文字サイズ）が後から来た | ○ | − | − | − | `docs/brief.md` |
| データの持ち主を後から作り直した | − | ○ | − | − | `docs/data-model.md` |
| デモデータで全部作ってからサーバーにつないだ | − | ○ | − | − | フェーズ4 |
| 公開の手続き（法務・審査・価格）を直前に知った | − | ○ | − | ○ | `docs/release.md` |
| git・ブランチ運用が崩れた | ○ | ○ | − | ○ | `CLAUDE.md` |
| 確認用スクリプトが一時フォルダにあって消えた | ○ | − | ○ | ○ | `scripts/` |
| CI・pre-commit・フォーマッターの方針がなかった | ○ | ○ | ○ | ○ | 設定ファイル一式 |

逆に、どのプロジェクトでも効いたのは次の3つです。

- **仕様書を先に作り、承認してから実装する**（Evently の DESIGN.md、Pawroom のコンソール）
- **AI が自分で画面を撮って確かめる仕組み**
- **AGENTS.md の「Expo の版は公式ドキュメントで確かめる」方針**

## 中身

```
app-starter/
├── README.md              ← この手順書
├── KICKOFF.md             ← 新しいプロジェクトで最初に AI に貼るプロンプト
├── RETRO_PROMPT.md        ← 作り終えたら AI に貼る振り返りプロンプト
├── CLAUDE.md              ← AI 向けのルール（雛形）
├── docs/
│   ├── brief.md           ← 企画1枚（MVP・やらないこと・対応範囲・名前）
│   ├── screens.md         ← 画面・遷移・操作の一覧
│   ├── data-model.md      ← データの持ち主と権限（バックエンドがあるときだけ）
│   ├── design.md          ← デザインの物差し
│   ├── verify.md          ← 確かめ方（自動／ブラウザ／実機でしか分からないこと）
│   ├── release.md         ← 公開に必要な手続き
│   └── decisions.md       ← 決めたこと・変えたことの記録
├── scripts/
│   ├── shot.mjs           ← Web 書き出しを3つの画面幅で撮影
│   └── preflight-build.mjs← ビルド前に git の状態を確認
├── .github/workflows/verify.yml
├── .prettierrc / .prettierignore / lefthook.yml / eas.json / .env.example
└── setup/
    ├── package-scripts.json   ← package.json に足す scripts
    ├── gitignore-append.txt   ← .gitignore に足す行
    └── app-json-checklist.md  ← app.json に最初から入れる項目
```

## 使い方（最短）

1. 正式なフォルダで `npx create-expo-app@latest <名前> --template blank-typescript` を実行する（一時フォルダで始めない）。
2. このフォルダの中身を、できたプロジェクトに上書きコピーする。`setup/` の内容は手で反映する。
3. `git init` → 最初のコミット。
4. AI に `KICKOFF.md` の中身を貼る。以降は下の手順どおりに進む。

## 立ち上げ手順

各フェーズの「完了の目安」を満たすまで次に進まない、が原則です。

### フェーズ0　企画を1枚にする（半日）

決めるのは、あとから変えると高くつくものだけです。

- 目的：**見本の再現か、良いプロダクトか**（Evently の最大の手戻り）
- 誰の何を解決するか、MVP の3機能、**やらないこと**
- 完成の基準（確かめられる形で）
- 名前・bundle ID・slug（仮でよいので固定する。同名アプリと商標も調べる）
- 収益（無料／有料／課金）、価格、配信する国
- 対応範囲：画面幅、iOS / Android / Web、文字サイズ、ダークモード、縦固定、タブレット
- 使うネイティブ機能 → Expo Go で足りるか、開発用ビルドが前提か

**完了の目安**：`docs/brief.md` が埋まっている。
**AI への頼み方**：「実装はまだしない。KICKOFF.md の質問に答えるので、brief.md にまとめて。そのあと厳しい評価者として採点し、MVP を3機能に絞る案を出して」

### フェーズ1　画面・操作・データを決める（半日）

- 画面一覧と遷移（すべてのタブと遷移先。押せない UI を残さない）
- 操作の割り当て（タップ・長押し・スワイプ・ピンチ）
- バックエンドがあるなら：主体と持ち物、誰が読めて誰が書けるか、無料と有料の境目

**完了の目安**：`docs/screens.md`（と `docs/data-model.md`）が埋まり、迷ったらここを見れば決まる。
**AI への頼み方**：「画面一覧と遷移図を作って。同じ指の動きがぶつかるところ、行き止まりの画面を指摘して」

### フェーズ2　デザインの物差しを決める（半日〜1日）

- トーン、参考アプリ3つ、シグネチャー（このアプリだけの形・言葉・動き）
- 主要3画面を **2〜3案描いて、見て選ぶ**（文字見本や言葉だけで決めない）
- 色・書体（最大2つ）・角丸・余白をトークンにする。アプリとサイトで同じものを使う
- アイコンの方向性

**完了の目安**：`docs/design.md` があり、選んだ案の画像が `docs/` にある。トークンが `theme/` にある。
**AI への頼み方**：「主要3画面を、書体と配色を変えて3案描いて画像で見せて。選んだら design.md と theme に落として」

### フェーズ3　土台を作り、実機で開く（0日目）

- テンプレートの設定一式を入れる（lint・整形・型・テスト・CI・pre-commit・CLAUDE.md）
- `npm run verify` と CI を緑にする
- `scripts/shot.mjs` が3つの画面幅で撮れることを確かめる
- **持ち主の実機で開く**。Expo Go の SDK の版がプロジェクトと合っているかもここで確かめる

**完了の目安**：実機で空の画面（全タブ）が開く。最初のコミットが済んでいる。
**AI への頼み方**：「テンプレートの設定を入れて、verify と shot.mjs が通るところまで。終わったらコミットして、実機で確かめてほしい点を3行で教えて」

### フェーズ4　本物の通り道を通す（1日目）

- バックエンドがあるなら：**ログイン → 1件保存 → 開き直して表示** を本番と同じサーバーで通す。データの出入り口を1か所にまとめ、デモデータも同じ入口から返す
- 開発用ビルド／TestFlight を1本通し、**日本語の端末で日本語で起動する**ことを確かめる
- `docs/release.md` の手続きを洗い出し、並行で始める（届出や書類は時間がかかる）

**完了の目安**：実機で本番相当のビルドが動く。公開手続きのチェックリストに担当と期限が付いている。

### フェーズ5　いちばん難しい部分を先に作る

技術的に一番不確かな部分（描画品質、同期、ジェスチャーなど）を、合格の基準を決めてから作ります。

**完了の目安**：`docs/verify.md` の基準を、自動チェックと実機の両方で満たす。
**AI への頼み方**：「〇〇を作る前に、合格の基準と、実機でしか分からない点を先に挙げて」

### フェーズ6　MVP の機能を1つずつ

1機能ごとに「仕様（短く）→ 完了の条件 → 実装 → verify → 撮影 → 実機 → コミット」。
思いついた機能は `docs/brief.md` の「あとで」に書くだけにして、その場で作らない。

**AI への頼み方**：「〇〇機能を、仕様と完了の条件を先に書いてから作って。各段階の終わりに verify と撮影をして、コミットして」

### フェーズ7　仕上げと点検

- 動き、触り心地、アクセシビリティ（文字サイズ、読み上げ、視差効果を減らす設定）
- `docs/design.md` の「AI っぽさの点検」で採点して直す
- 独立した点検エージェント（見た目・動作担当と、コード・Android 担当）

### フェーズ8　公開

ストアのスクリーンショットは**最後に**撮る。審査メモとデモ動画を用意してから出す（`docs/release.md`）。

### フェーズ9　振り返り

`RETRO_PROMPT.md` を AI に貼り、この README と雛形を更新する。

## アプリの種類による分かれ道

| | フロントだけ（Evently・Lento・Inchly） | バックエンドあり（Pawroom） |
| --- | --- | --- |
| `docs/data-model.md` | 不要（モックデータの型だけ決める） | **必須**。フェーズ1で決める |
| データの出入り口 | モックを1か所にまとめる | 画面がサーバーを直接さわらない層を置く。デモモード付き |
| フェーズ4 | 開発用ビルド／TestFlight を通す | 加えてログイン→保存→表示を通す |
| テスト | レイアウトなどの純粋関数 | **中心の流れ**（保存→再読み込み、課金による権限）を必ず |
| 権限ルール | − | アプリとサーバーの両方に書かない。サーバーを正にする |
| `.env.example` | 不要なら置かない | 公開してよい鍵かどうかを注記する |
