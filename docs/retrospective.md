## 1. プロジェクト概要

- **アプリの種類・規模**：小中高生向けの iPhone 勉強記録アプリ「Inchly」。勉強時間のタイマー、時間割、記録と草（GitHub の草のような表）、連続日数、友だち、タイムラインがある。あわせて紹介サイト（LP）も作った。［事実］約1か月で 219 コミット。アプリは `src/` の下に画面・部品・テーマが数十ファイルあり、テストは 213 件。
- **技術スタック**［事実］
  - 言語：TypeScript（`typescript ~6.0`）
  - フレームワーク：Expo SDK 58 / React Native 0.88 / React 19 / Expo Router（`src/app/` がルート）
  - 動き・描画：react-native-reanimated 4.7、react-native-gesture-handler 3、@shopify/react-native-skia、react-native-svg、expo-glass-effect、expo-blur
  - 状態と保存：自前の小さなグローバルストア（`src/store.ts`）を AsyncStorage に保存。**サーバー・DB・認証の本物はまだない**（サインインの画面と「サンプルのアカウント」だけ）
  - 通知：expo-notifications（端末内の通知）
  - フォント：@expo-google-fonts を 15 種類
  - 品質：ESLint（`eslint-config-expo`）、`tsc --noEmit`、Jest（`jest-expo`）
  - 動かし方：Expo Go（実機）＋ web（`npx expo start --web`）＋ 自前の `npm run live`（20 秒ごとに git pull）
  - 紹介サイト：素の HTML / CSS / JS（`site/`）
  - ホスティング・CI・EAS：**なし**（`eas.json`・`.github/`・`.env` はない）

### 手戻り・詰まったこと

1. **見た目の方向が何度もひっくり返った**
   - 何が起きたか［事実］：10-21 の1日で見た目を5回以上変え、そのうちいくつかは元に戻した。そのあとも、パステルとすりガラス → 鯉の池と白いガラス → サイトに合わせた紙・インク・ライムへと大きく変わった。
   - 原因［意見］：「誰に、どう感じてほしいか」と「やらない見た目」を書いた物差しがなかった。その場の印象で決めていた。
   - 防ぐには：最初に**デザインの芯の1枚**（読み手、3つの形容詞、参考と反例、色・字・角・影・動きの決まり）を作り、モックで1回だけ選ぶ。

2. **MVP の範囲が決まらないまま、広く作った**
   - 何が起きたか［事実］：テーマ 10 種以上、背景3種、コイン・ショップ・ミッション、iPad と PC のモックを作った。その多くを消すか、閉じるか、後回しにした。
   - 原因：仕様書に「MVP」「やらないこと」の章がなかった。
   - 防ぐには：仕様の最初の章を **MVP の範囲と、やらないことの一覧**にする。足すたびにその表を見る。

3. **Expo SDK と Expo Go の版が合わなかった**
   - 何が起きたか［事実］：SDK 58 で作り始め、同じ日に 57 へ下げ（「Project is incompatible with this version of Expo Go」）、7日後に 58 へ戻した。README に対処の手順の章がある。
   - 原因：持ち主の iPhone の Expo Go が、どの SDK に対応しているかを先に確かめていなかった。
   - 防ぐには：0日目に、空のアプリを**持ち主の実機で開く**ところまで済ませる。

4. **web で確かめても、実機ではずれた**
   - 何が起きたか［事実］：持ち主が「カードの下が切れてる」と言った。iOS では、輪郭や影がスクロールの枠に切られ、字の上も欠けていた（ドット文字や大きな数字）。どれも web のスクショでは見えなかった。ドット文字も、実機で「細くて読みにくい」と言われた。
   - 原因：確かめるのが web の Playwright だけで、実機で撮る手順も、確かめるリストもなかった。
   - 防ぐには：開発ビルドかシミュレーターで撮る手段を最初に用意する。それができないなら、「実機で見る点」のリストを毎回渡す。

5. **動きのルールがあとから来た**
   - 何が起きたか［事実］：ばね・ぷるん・ポップ・ずっと動く飾りを作ったあとで、`MOTION.md`（跳ねない、トークンだけ、transform と opacity だけ）を決め、lint とテストで止めるようにした。
   - 防ぐには：動きの決まりを、最初の部品より先に書く。

6. **テストが遅かった**
   - 何が起きたか［事実］：最初のテストは 10-22（日付の持ち方の作り直しのとき）。日付・日をまたぐ記録・連続日数の計算は、何度も直した。
   - 防ぐには：時間や日付のロジックは、最初から純粋な関数に分けてテストを付ける。

7. **作業の環境まわりで止まった**
   - 何が起きたか［事実］：
     - 会話の言葉：持ち主は日本語で話していたが、私が英語で答え、2回注意された（「日本語で これ厳守」）。
     - 利用制限：5時間ごとの上限で、並べて動かしていた作業が2回止まった。
     - 自動コミット：作業の終わりに「コミットして push」を求めるフックがあり、途中の状態が何度も push された。`npm run live` があるので、それがそのまま持ち主の iPhone に届いた。
     - 作業環境の再起動：何度か起き、そのたびにローカルのサーバーが止まった。
   - 防ぐには：
     - 言葉と書き方の決まりを `CLAUDE.md` に最初に書く。
     - 大きな作業は小さく区切る。
     - 途中の状態は別のブランチに置き、`live` は確かめた版だけを取り込む。

8. **アプリとサイトがずれた**
   - 何が起きたか［事実］：サイトは参考サイトに寄せ、アプリは別の見た目だったので、あとでアプリのスタンダードを丸ごと作り直した（クラシックとして前の見た目を残した）。
   - 防ぐには：ブランドの芯（ロゴ・色・字・形）を、アプリとサイトで1つにしてから両方を作る。

## 4. 最初に決めておくべきこと

### 仕様・スコープ
- **MVP の範囲**：画面の数、機能、テーマは1つだけ、背景はなし、プラットフォームは iPhone のみ。［事実］最後にそう決まった。
- **やらないことの一覧**：iPad と PC の版、テーマの着せ替え、背景、コインやショップ、ウィジェット、広告。最初はすべて「後で」に置く。
- **お金の取り方**：広告か、サブスクか、なしか。［事実］今も決まっていない（タイマーに広告の見本がある）。画面の形に響く。
- **対象年齢と安全**：小学生も使うか、保護者の同意、友だち機能の公開の範囲。［事実］途中で「小学生から」「13 歳未満は保護者の同意」と決まった。友だち・メッセージの作りに響くので、最初に決めておきたかった。

### 技術選定
- **Expo SDK の版**：持ち主の Expo Go に合わせる。開発ビルド（EAS）を使うかどうかも決める。ウィジェットや一部のネイティブ機能は、開発ビルドがないと作れない。
- **データをどこに置くか**：端末だけか、サーバー（Supabase・Firebase など）か。［事実］今は端末だけで、友だち・タイムライン・ランキングは見本のデータ。**ここが一番大きな未決**。
- **認証**：Apple・Google・メールでサインインするか。［事実］画面だけある。
- **状態管理**：［事実］自前の小さなストアで足りていた。
- **動きのライブラリと決まり**：Reanimated と `MOTION.md` の決まり（跳ねない、トークンだけ、transform と opacity だけ）。
- **フォント**：日本語はシステムフォント。飾りの書体は、使う大きさごとに決める（ドット文字は 16 の倍数だけ）。

### 設計・構成
- **ディレクトリ構成**：［事実］`src/app`（ルートだけ）、`src/screens`（画面）、`src/ui`（部品）、`src/lib`（計算とテスト）、`src/themes/<id>`。この形は最後まで持った。
- **テーマの仕組み**：［事実］「共通の描き方＋テーマの kit」。ただ、スタンダードが共通の土台を兼ねていたので、作り直しのときに「クラシック」という逃げ道が必要になった。最初から「土台」と「見た目」を分けておくのがよい。
- **データモデル**：記録（開始時刻・分・科目 id）、予定（曜日・時刻・長さ）、日付の区切り（日をまたぐ記録は日付ごとに分ける）。
- **API**：［意見］サーバーを使うなら、記録の同期と友だちのデータの形を最初に決める。

### ルール
- **言葉**：会話・コミット・画面の文は日本語、コードのコメントは英語で短く。［事実］途中で決まった。
- **ブランチ運用**：決まったブランチに push、PR は作らない。［事実］途中の状態も push され、それが `live` で実機に届いた。
- **確かめる手順**：lint・型チェック・テスト・画面の撮影。［事実］`AGENTS.md` に書かれていた。
- **使ってはいけないもの**：ほかのブランドのロゴ・キャラ・専用の書体、グラフに緑、跳ねる動き。［事実］会話とファイルで少しずつ決まった。
- **エラー処理**：［事実］はっきりした方針はなかった。保存の失敗は黙って捨てている（`.catch(() => {})`）。

## 5. 最初にセッティングしておくべきもの

### 開発環境
- **lint**：`eslint.config.js`（`eslint-config-expo`）。［事実］あとで、跳ねる動きの書き方も lint で止めるようにした。最初から入れておく。
- **formatter**：［事実］なかった。Prettier（または Biome）と保存時の整形を最初に入れる。
- **型チェック**：`tsconfig.json`（strict）と、`@/` の別名。
- **テスト**：`jest-expo`、`src/lib/__tests__/`。日付・時刻・記録・連続日数の計算に、最初からテストを付ける。
- **pre-commit**：［事実］なかった。lint と型チェックと関係するテストを、コミットの前に回す（husky + lint-staged など）。
- **実機への取り込み**：`scripts/live.mjs`（`npm run live`）。［事実］とても効いた。ただし、確かめた版だけを取り込むように、取り込むブランチを分ける。

### 設定ファイル
- **`app.json`**：名前、bundle id、アイコン、スプラッシュ、向き、通知の権限の文。
- **`.env.example`**：［事実］なかった。サーバーを使うならキーの名前だけ書く。
- **`eas.json`**：［事実］なかった。ウィジェットやストアに出すなら、開発ビルドの設定を最初に作る。
- **CI**（`.github/workflows/ci.yml`）：［事実］なかった。lint・型チェック・テストを push のたびに回す。
- **`.gitignore`**：［事実］Expo のテンプレートのもの。画面写真などの大きなファイルの置き場所も決めておく。`docs/` は 45MB になった。

### AI 向けの準備
- **`CLAUDE.md`**（リポジトリの一番上）［事実］なかった。`inchly-app/AGENTS.md` だけで、ルールは会話や `MOTION.md` に散らばった。書いておくとよい内容の案：
  - **言葉**：返事・コミット・画面の文は日本語（厳守）、コメントは英語で短く、小中高生が読めるやさしい文。
  - **MVP の範囲とやらないこと**（2章の表へのリンク）
  - **デザインの芯**：トークン、使わない見た目、グラフに緑を使わない、ほかのブランドのロゴ・キャラ・書体は使わない。
  - **動きの決まり**：`MOTION.md` を読んでから動きに触る。
  - **確かめ方**：`npx expo lint`・`npx tsc --noEmit`・`npx jest`、web で 375・390・430 の幅を撮って見ること。実機でしか分からない点は報告に書くこと。
  - **パッケージ**：`npx expo install` を使う。Expo の資料は版ごとのものを読む（`AGENTS.md` の中身）。
  - **git**：ブランチ名、コミットの書き方、PR は作らない、途中の状態の扱い。
  - **ファイルの地図**：画面・部品・テーマ・ストアの場所（README の表の要約）。
- **最初に AI に渡す資料**：調査の要約、仕様（MVP の章つき）、画面一覧、デザインの芯、参考と反例の画像、持ち主の実機の情報（iPhone の機種、Expo Go の版）。
- **頼み方**：「モック → 選ぶ → 実装 → web で撮る → 実機で見る点を報告」の流れを、最初に決めておく。

### その他
- **見本のデータ**：［事実］`src/data.ts` の見本のアカウント（はる）と「サンプルのアカウントで見る」。画面を確かめるのにとても役立った。最初から用意する。
- **保存の形の版**：［事実］ストアに版の番号（`VERSION`）と読み直しの処理がある。最初から入れておく。
- **DB マイグレーション**：［意見］サーバーを使うなら、最初から migration の仕組みを入れる。
- **デプロイ**：［意見］紹介サイトの置き場所（Vercel・Cloudflare Pages など）と、TestFlight までの道を、MVP の前に一度通しておく。

## 6. もしゼロからやり直すなら：理想の立ち上げ手順

1. **調査と要件**
   - やること：読み手、困りごと、今使っているもの、勝ち筋を1枚にまとめる。
   - 完了の目安：「誰の何を、どう良くするか」が3行で言える。
   - AI への頼み方：「この分野の調査を、出典つきで1枚にまとめて。結論は3行で」
2. **MVP の範囲を決める**
   - やること：機能を「MVP／あと／やらない」に分ける。画面一覧と流れの図を作る。
   - 完了の目安：MVP の画面が10以下で、やらないことの一覧がある。
   - AI への頼み方：「この仕様を MVP・あと・やらないに分けて。MVP は1週間で作れる量に。理由も1行ずつ」
3. **ブランドとデザインの芯**
   - やること：名前と商標の確認、ロゴ、トークン（色・字・角・影・余白）、動きの決まり（`MOTION.md`）、反例。アプリとサイトで同じものを使う。
   - 完了の目安：`DESIGN.md` と `MOTION.md` がある。
   - AI への頼み方：「方向の違うモックを3案、HTML で作って。採点して、決めたら DESIGN.md に書いて」
4. **さわれるモックで大事な画面を決める**
   - やること：ホーム・タイマー・記録の HTML モックを作り、iPhone で見て1つ選ぶ。
   - 完了の目安：選んだ案の写真と、決めたことのメモがある。
   - AI への頼み方：「この3画面の HTML モックを、390 の幅で、さわれる形で作って公開して」
5. **0日目の土台**
   - やること：Expo のテンプレート（持ち主の Expo Go の SDK に合わせる）。lint・formatter・型チェック・テスト・CI・pre-commit。`CLAUDE.md`。`npm run live`。見本のデータ。
   - 完了の目安：空のアプリが持ち主の iPhone で開き、CI が緑。
   - AI への頼み方：「このテンプレートどおりに土台を作って。持ち主の iPhone で開けるところまで確かめて」
6. **データモデルと計算**
   - やること：記録・予定・科目・日付の型と、純粋な計算（今日の合計・連続日数・日をまたぐ記録）を書き、テストを付ける。
   - 完了の目安：計算のテストが通る。
   - AI への頼み方：「先にテストを書いてから、計算を実装して」
7. **MVP の画面を作る**
   - やること：1画面ずつ、決めたデザインの芯で作る。毎回 web で3つの幅を撮って見る。実機で見る点を報告する。
   - 完了の目安：`UI-CHECK.md` の項目が全部済み。
   - AI への頼み方：「この画面を作って。lint・型・テストを通し、375・390・430 で撮って、違和感を直してから報告して」
8. **持ち主の実機での確かめと仕上げ**
   - やること：実機で全画面を見て直す。テストを担当の人と別の人の目で、通しで見直す。
   - 完了の目安：持ち主が「これで出す」と言う。
   - AI への頼み方：「全画面を通しで見直して、切れ・重なり・読みにくさを直して」
9. **出す準備**
   - やること：認証とサーバー（使うなら）、プライバシーポリシーと利用規約、紹介サイト、App Store の素材、TestFlight。
   - 完了の目安：TestFlight で持ち主以外の人が使える。
   - AI への頼み方：「出すまでのチェックリストを作って、1つずつ進めて」

## 7. テンプレートに入れる / 入れないもの

### 入れる（どのアプリでも使える）
- `CLAUDE.md` のひな形（言葉、MVP、デザインの芯、動き、確かめ方、git）
- `MOTION.md` の考え方（跳ねない、トークンだけ、transform と opacity だけ、lint とテストで止める）
- `UI-CHECK.md`（画面ごとの確かめリストと、状態の記号）
- `MEMO.md`（決まっていないアイデアの置き場。決まったら README へ）
- `scripts/live.mjs`（push を実機に取り込む）
- 見本のデータと「サンプルのアカウントで見る」
- ストアの保存の版と読み直し
- テーマの仕組み（共通の土台と、見た目の kit を分ける。出すかどうかの切り替え）
- Playwright で画面を撮る小さな道具（3つの幅、見本のアカウント、テーマの切り替え）
- 「モック → 採点 → 選ぶ → 実装 → 撮る → 直す」の流れと、デザインスキルでの評価のやり方
- CI・pre-commit・formatter の設定

### 入れない（Inchly だけのもの）
- 勉強・時間割・草・連続日数・EXP とレベルなどの中身と計算
- 住人（ペンタ・ボッ・めぶ など）、サイバーなどのテーマの絵
- 鯉の池・サメ・歩く人の背景
- 紹介サイトの「放課後から夜まで」と、参考サイトの言語化
- 名前の調査・調査レポートの中身
- 小学生・保護者の同意まわりの決まり（対象が違えば変わる）

## 8. どのアプリにも通用する教訓 TOP3

1. **最初に「MVP とやらないこと」を書き、足すたびにその表を見る。**［事実］テーマ 10 種、背景3種、ショップ、iPad と PC の版を作って、あとで閉じたり消したりした。範囲の線が最初にあれば、その時間は MVP の仕上げに回せた。
2. **見た目は「物差し」を先に決めてから、モックで1回だけ選ぶ。**［事実］見た目は1日に5回変わり、アプリとサイトがずれて丸ごと作り直した。デザインの芯（読み手・形容詞・反例・トークン・動き）をアプリとサイトで1つにしてから作ると、ひっくり返らない。
3. **0日目に「持ち主の実機で開く」と「確かめの仕組み」を通す。**［事実］SDK の不一致で版を2回替え、web では見えない切れや細い字が実機で見つかった。実機で開ける土台、テスト、CI、撮影の道具、それに「実機で見る点」のリストを、最初のコードより先に用意する。
